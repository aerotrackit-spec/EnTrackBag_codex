STATUS DEFINITIONS
- Online: device is powered and communicating normally over the network.
- Warning: device is reachable, but an abnormal condition requires attention.
- Offline: device is not communicating or is unavailable on the network.

Warning must not be fabricated. Use an approved rule based on actual alarm/error data if required.

ANTENNA RULES
- Preserve Reader -> Antenna relationship through existing ReaderID.
- One antenna record must not be assigned to multiple readers.
- An FX9600 has 8 ports, but never assume 8 ports = 8 physical antennas.
- Count configured Antennas rows for the ReaderID when appropriate.
- Physical single-pin/double-pin grouping is unknown unless the existing system explicitly represents it.
- Show configured/used ports and their status.
- Connected = Green.
- Not Connected = Red.
- Unused/not configured port = Idle/neutral.
- Do not invent physical antenna counts.

IMPORTANT:
- Do not create an artificial repository abstraction for every table unless it provides real domain/application value.
- Keep BLTSMFT schema mapping in Infrastructure.
- Do not move database-specific column knowledge into Domain entities unnecessarily.
- Keep business rules in Domain/Application rather than Controllers.
- Organize by business capability/feature where practical so changes to Device Status, SLA, Tag Report, or Bag Journey remain isolated.
- Preserve clear separation between read/query models and domain behavior where appropriate.
- The structure must make it possible to modify one feature without creating a chain of unrelated changes throughout the application.

AUTHENTICATION

Authentication answers:

    "Who is the user?"

Typical flow:

    Browser
       |
       v
    TrackIT Identity
       |
       v

       |
       +----------------------+
       |                      |

TOKEN HANDLING

The architecture must support JWT/OIDC-style bearer authentication.

The API validates the access token.

The SignalR connection is authenticated using the same user access token.

The user's identity, roles, and permissions should be available to the application authorization layer.

Do not require the EnTrackBag API to call the Identity service for every request merely to ask whether a token is valid.

Prefer normal token validation locally in the API/hub, while the Identity service remains the authority that issues tokens.

APPLICATION ISOLATION

The shared Identity service must remain independent from EnTrackBag's baggage domain.

Do NOT put:

- User entities
- Role entities
- Permission entities
- authentication logic

inside:

    EnTrackBag.Domain

unless there is a specific integration contract/value needed by the application.

EnTrackBag should consume the authenticated identity/claims and apply application-specific authorization policies.

SECURITY ACCEPTANCE CRITERIA

- Authentication is centralized in TrackIT.Identity.
- Authorization is reusable across TrackIT applications.
- JWT/OIDC access tokens protect REST APIs.
- The same authenticated token/user context protects SignalR/WebSocket connections.
- SignalR hubs require authentication.
- Hub operations are authorization-aware.
- Angular cannot bypass backend authorization.
- EnTrackBag does not store authentication credentials in BLTSMFT.
- Identity data is stored separately from BLTSMFT.
- No separate SignalR login is implemented.
- Identity is not tightly coupled to the EnTrackBag domain.
- Future TrackIT applications can reuse the Identity service.
- No fake authentication, users, roles, permissions, or tokens are added as production data.
